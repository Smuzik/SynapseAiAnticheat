## 0. Резюме для быстрого чтения

Прочитаны все ключевые файлы обоих проектов и эмпирически протестирована ONNX-модель (через `onnxruntime`). Два симптома, которые тебя беспокоят, имеют конкретные, подтверждённые в коде причины — и обе оказались **не там, где кажется на первый взгляд**.

**Симптом 1 — ложные срабатывания (крит с разворотом на 360° по игроку в углу).**
Виноват **не ИИ**. Прямой тест показал: ONNX-модель выдаёт максимум ~0.33 вероятности даже на явный чит-вектор, а порог `min_confidence = 0.75`. То есть ИИ-ветка почти никогда не срабатывает. Ложные баны/кики идут от **синхронных «hard-checks»** (`HardCombatChecks`): Reach, HitboxBypass и особенно **HardSnap**, которые ловят легитимный быстрый бой, потому что:
- нет компенсации задержки (лаг-компенсации) — хитбокс жертвы берётся «здесь и сейчас», без буфера прошлых позиций по пингу;
- нет анализа контекста (стены, угол, отбрасывание/knockback, скорость, прыжок, крит, смена цели, пинг);
- `shouldCancelDamage` молча отменяет легитимные удары (игрок думает, что «сервер лагает»);
- `punishments.hard.flags_to_kick = 1` → кик за **одно** срабатывание, без накопительного риск-скора.

**Симптом 2 — язык переспрашивается после выбора.**
Две причины, обе подтверждены: (1) `AiAnticheatPlugin.sendHelpMenu()` **безусловно** вызывает `sendLanguageSelectorPrompt()` при каждом `/aiac`; (2) выбор языка хранится в `LanguageManager` в оперативной памяти (`Map<UUID,String>`) и **никогда не сохраняется на диск** → теряется при перезапуске/reload.

**Бонусом найдено (важно):** серьёзный train/serve skew в ИИ (модель обучена на знаковых значениях, а в рантайме к ним применяется `Math.abs()` + перепутан порядок признаков), модель обучена на 100% синтетических читах против реальных данных с меткой UNKNOWN, `synchronized` на инференсе убивает пул из 2 потоков, хардкод русского в GUI/статусах/plugin.yml, O(n²)-скан в коллекторе на главном потоке, отсутствие метаданных версий в датасете.

Ниже — детальный разбор и поэтапный план. В конце — вопросы, по которым нужно твоё решение перед началом «огромных правок».

## Часть 1. Аудит Freecam PvP Collector

### 1.1 Текущая архитектура
Клиентский мод собирает телеметрию PvP и пишет её в CSV.

```
клиентский тик → CombatTracker (скан всех игроков, O(n²)) → TelemetrySample → CsvDatasetSink (async-поток) → CSV
              ↘ AutoWatchController (авто-наблюдение)   ↘ FreeCamController / CameraMixin
```

Команды: `/pvprecorder` (start, stop, target, label, source, antiafk, status, auto, watch, unwatch), `/freecam`, `/antiafk`. Хоткеи F6–F9.

### 1.2 Найденные проблемы

**Критические / архитектурные**

- **`CombatTracker` работает на главном потоке Minecraft и делает вложенный цикл по всем игрокам (O(n²)) каждый клиентский тик.** На людных серверах это прямой удар по FPS. Вся тяжёлая работа (гео-расчёты, история, сериализация признаков) должна уйти в worker-поток через lock-free очередь.
- **`CombatPairState.rotationHistory` — это `LinkedList`, к которому обращаются по индексу `.get(i)`** (O(n) на каждый доступ). Для окна истории нужен кольцевой буфер на массиве (O(1)).
- **Нет автономного ИИ-модуля вообще.** Классификация CHEAT/LEGIT/UNKNOWN сейчас невозможна на стороне коллектора — только ручная разметка через `/pvprecorder label`. Это и есть то, что ты хочешь убрать.

**Схема датасета (`TelemetrySample`, 49 полей)**

Отсутствуют поля, которые ты явно требуешь:
- `model_prediction`, `confidence`, `uncertainty`
- `label_source` (HUMAN / AI / HYBRID / UNKNOWN) — сейчас метка есть, а источник метки не различается на уровне схемы
- `model_version`, `collector_version`, `feature_schema_version`, `dataset_version`

Плюс два «затычных» значения: `estimatedServerTps` захардкожен как `20.0f`, `clientVersion` захардкожен `"26.2"` в `SessionManager`.

**Мелкие/качество кода**

- `AutoWatchController` пересоздаёт `new Random()` в цикле (строки ~195, 200) — нужно один экземпляр в поле.
- Тайминги авто-наблюдения похоже расходятся с комментариями (`MIN_WATCH_TICKS = 20*20 = 400` тиков = 20 c при комментарии «5 минут»). Требует ревизии.
- Все чат-строки захардкожены. Для клиент-мода это некритично (в отличие от серверного плагина), но стоит вынести хотя бы ключевые.

### 1.3 Что хорошо (сохраняем)
- `CsvDatasetSink` уже асинхронный (отдельный поток + `ConcurrentLinkedQueue`) — правильная идея, доработаем батчинг.
- Разделение `FreeCamController` / `CameraMixin` аккуратное, привязка только к `Camera.update()` (в MC 26.2 это корректно).
- `SessionManager` уже хеширует игроков (SHA-256 с солью) — приватность на уровне.

## Часть 2. Аудит Purpur AI Anticheat

### 2.1 Текущая архитектура

```
EntityDamageByEntityEvent (LOW, главный поток)
   ├─ TPS-protection
   ├─ HardCombatChecks.evaluate()  ── синхронно, может отменить урон и кикнуть (1 флаг)
   └─ InferenceService.submitAnalysis() ── async (2 потока) → AiInferenceEngine.predict() [synchronized!]
PlayerMoveEvent (MONITOR) → KinematicHistory.push()
GrimAcBridge (reflection) → вливает флаги Grim
Alert/Overhead/Freeze/Punishment/Webhook/GUI менеджеры
```

Идея пайплайна в целом здравая (события → признаки → инференс → снапшот → решение), но реализация имеет критические дефекты.

### 2.2 Критические проблемы

**(A) Ложные срабатывания — главный приоритет.**
Разобрано в резюме. Ключевое в `HardCombatChecks.java`:
- **Reach:** `calculatedReach > 3.25` → `shouldCancel=true`; `>= 3.65` → флаг. Дистанция считается до текущей серверной позиции жертвы. При отбрасывании/пинге/крите eye-to-eye легко «прыгает» за 3.25 м → отменённый урон и/или флаг.
- **HitboxBypass:** `!raycast.hit() && angleOffset > 70°`. Во время разворота в момент тика луч может не попасть в (рассинхронизированный) хитбокс.
- **HardSnap:** `angularVel>90 && yawAccel>75 && angleOffset<5 && !raycast.hit()`. Быстрый крит-разворот на 360° даёт и высокую угловую скорость, и ускорение; если в момент проверки луч промахнулся (угол/стена/десинк), но игрок в итоге «на цели» — **срабатывает**. Это ровно твой кейс «360° по игроку в углу».
- **Лаг-компенсации нет:** только статическое расширение хитбокса на `0.10–0.25 м`. При 100 мс пинга реальная позиция цели может отличаться на ~0.5–1 блок. Настоящие античиты (Grim) хранят историю позиций жертвы и проверяют по всему окну пинга — здесь этого нет.
- **Наказание мгновенное:** `hard.flags_to_kick = 1`. Нет накопительного риск-скора с распадом для hard-веток.

**(B) Язык переспрашивается.** `sendHelpMenu()` всегда зовёт `sendLanguageSelectorPrompt()`; `playerLanguages` не персистится. (Детали в резюме.)

**(C) Train/serve skew в ИИ.** `FeatureVector.getInferenceInput16()`:
- применяет `Math.abs()` к yaw/pitch-дельтам и ускорениям, хотя модель обучена на **знаковых** значениях (знак ускорения — это как раз то, что отличает человеческое торможение от роботизированного снапа; в комментарии к `createV1` прямо написано «Do NOT apply Math.abs()», но в `getInferenceInput16` он применён);
- **порядок признаков перепутан** относительно обучения. Обучение: `distance, angle_off, yaw1/2/5, yawAcc, pitch1/2/5, pitchAcc, raycast_hit, raycast_dist, raycast_ang_err, is_falling, is_sprint, atk_cd`. А в рантайме слот 0 = `raycastDistance`, слот 10 захардкожен `1.0`, слот 11 = `distanceMean`, слот 12 = `targetAngleDeg`. Четыре слота получают не тот признак.

Эмпирическая проверка (я прогнал модель напрямую): стрип знака **почти утроил** подозрительность на легитимном флике (0.065 → 0.17). Модель максимум выдаёт ~0.33 даже на явном чите.

**(D) Данные обучения модели.** CHEAT-примеры на 100% синтетические (numpy-генерация killaura/reach/closet). Реальный датасет `combat_extracted_dataset.csv` (200k) целиком помечен `label_source=OBSERVATION / label=UNKNOWN` и обучается как «легит» (y=0). Модель не видела ни одного реального чита → она в принципе не способна их надёжно ловить. Это объясняет и низкую вероятность на чит-векторах.

**(E) `AiInferenceEngine.predict(...)` объявлен `synchronized`.** Это сериализует весь инференс и обнуляет смысл пула из 2 потоков в `InferenceService`. Плюс `inputTensor` может утечь, если `session.run` бросит исключение (нет try-with-resources/финализации).

### 2.3 Локализация и хардкод (нарушает твоё требование «локализовать ВСЁ»)

- **`AdminGuiManager` — весь GUI на русском хардкоде**, полностью в обход `LanguageManager` («Панель Администратора», «ИИ-Диагностика Боя», «Вызвать на проверку» и т.д.).
- **`ThreatState.displayTag` — хардкод русского** («ЧИСТ», «ПОДОЗРЕНИЕ», «ВЫСОКИЙ РИСК», «ПОДТВЕРЖДЕН»); `getDisplayTag()` всегда возвращает русский вне зависимости от языка игрока.
- **`FreezeManager` — десятки русских строк** (тайтлы, чат проверки, сообщения о заморозке).
- **`PunishmentManager`** — русские шаблоны кика/бана по умолчанию.
- **`CombatListener` строка 64** — русский алерт про заход с забаненного IP.
- **`PlayerProfile.lastFlagReason = "Нет"`** — русское значение по умолчанию.
- **`DiscordWebhookService`** — тело embed целиком на русском (можно оставить как настраиваемый шаблон, но не хардкодить).
- **`plugin.yml`** — описания команд на русском.
- **`messages_en.yml` содержит русские «протечки»** (автор «Даня», `lang_selector.*` с русским текстом внутри английского файла).
- **Нет ключей** для GUI, состояний угрозы (ThreatState), причин детекта — их ещё предстоит завести.

Фундамент правильный (translation-key подход в `LanguageManager` с подстановкой `{placeholder}` уже есть) — нужно достроить его и перевести на него все строки.

### 2.4 Объяснимость, калибровка, риск-движок

- **Нет накопительного Risk Score с распадом для комбинирования сигналов.** Сейчас: hard-флаг → мгновенно; ai-флаг → счётчик до порога кика. Требуется единый риск-движок, который агрегирует сигналы (aim/movement/combat/rotation/attack-timing/packet/context), применяет калиброванные пороги и распад.
- **Пороги калибровки (low/medium/high_confidence) отсутствуют в `config.yml`** и, соответственно, не участвуют в решении. Есть только `min_confidence: 0.75`.
- **Объяснимость слабая.** Есть `getPrimaryViolation()` и процент уверенности, но нет структурированного набора сигналов/причин с весами и уровнем неопределённости.

### 2.5 Производительность
- `synchronized` инференс (см. 2.2E).
- `KinematicHistory` — снова `LinkedList` с доступом по индексу (O(n)).
- `HardCombatChecks` + два вызова `raycastTargetHitbox` на каждый удар на главном потоке.
- `OverheadDisplayManager` спавнит `TextDisplay`-сущности и телепортирует их 5 раз/сек — при большом онлайне стоит проверить нагрузку (differential-update уже есть — это плюс).
- TPS-protection есть (при TPS < 17.5 проверки пропускаются) — хорошая идея, оставляем.

### 2.6 Что хорошо (сохраняем)
- Модульность менеджеров (Alert, Freeze, Punishment, Overhead, Webhook, Gui, Bridge) — разумное разделение.
- `DetectionSnapshot` — иммутабельный record с билдером.
- `GrimAcBridge` через reflection — аккуратный опциональный мост.
- `CompatUtils` — единая точка для hex-цветов/компонентов.
- Асинхронный `DiscordWebhookService`, differential overhead-дисплеи, TPS-protection.

## Часть 3. Совместимость схем данных (между проектами)

Сейчас признаки существуют в **трёх несогласованных представлениях**:

| Представление | Где | Проблема |
|---|---|---|
| 49 «сырых» полей | `TelemetrySample` (коллектор) | нет version-метаданных, prediction, label_source |
| 16 признаков обучения | Python `FEATURE_NAMES` | знаковые, порядок A |
| 18 именованных + `getInferenceInput16()` | `FeatureVector` (анти-чит) | 16 из них в **другом** порядке, с `abs()` |

Это и есть корень train/serve skew. Нужна **единая версионированная схема признаков** — один источник истины, используемый одинаково в извлечении (Python), обучении (Python) и инференсе (Java), с полем `feature_schema_version`, сохраняемым и в датасете коллектора, и в предсказаниях анти-чита. Тогда коллектор и анти-чит говорят на одном языке, а модель переобучается без риска рассинхрона.

## Часть 4. Ограничения окружения (честно)

- В песочнице есть `onnxruntime` (могу запускать/инспектировать текущую модель), но **нет `scikit-learn`/`skl2onnx`/`onnx` и нет сети для установки** → **переобучить модель и пере-экспортировать ONNX прямо здесь я не смогу.** План: (1) чинить Java-инференс, (2) отдать тебе исправленные, воспроизводимые Python-скрипты обучения/извлечения с корректной схемой и стратегией разметки — их ты запустишь там, где стоит sklearn, (3) снижение ложных срабатываний сделать в детерминированном Context/Risk-движке (переобучение для этого не нужно).
- В воркспейсе `java 11`, а проекты требуют Java 17 (анти-чит) и Java 25 (коллектор). Полная Gradle-сборка в песочнице может быть недоступна, если toolchain не скачает нужный JDK. Буду проверять сборку и честно сообщать, если собрать локально нельзя.
- Никаких выдуманных бенчмарков: где нет реальных замеров TPS/MSPT/FP-rate — прямо укажу, что и как нужно измерить.

## Часть 5. План изменений (поэтапно, по приоритету)

**Фаза 0 — Фундамент.** Единая версионированная схема признаков (один источник истины для Python и Java). Каркас тестов/сценариев. Проверка сборки обоих проектов.

**Фаза 1 — Анти-чит: устранение ложных срабатываний (ГЛАВНОЕ).**
- Лаг-компенсация: буфер позиций жертвы по окну пинга, проверка reach/hitbox по всем позициям окна.
- Context Engine: стены/угол, knockback, скорость, прыжок, крит, смена цели, пинг, тайминги пакетов.
- Risk Engine: накопительный скор с распадом, агрегирующий сигналы; калиброванные пороги low/medium/high из конфига, реально применяемые в решении.
- Убрать «мгновенный кик за 1 hard-флаг» и «тихую отмену урона» для пограничных случаев; hard-ветка тоже кормит риск-скор.
- Кейс «360° в углу» → отдельный регресс-тест, который обязан быть LEGIT.

**Фаза 2 — Анти-чит: корректность ИИ.**
- Починить `getInferenceInput16()`: знаковые значения, правильный порядок, реальные `raycast_hit / raycast_distance / raycast_angle_error`.
- Снять `synchronized` с `predict`, чинить утечку тензора (try-with-resources), сделать инференс реально параллельным/батчевым.
- Объяснимость: структурированные сигналы + причины + уверенность + неопределённость; `model_version` в каждом предсказании.
- Исправленный, версионированный Python-пайплайн обучения/извлечения (запуск — на твоей стороне, где есть sklearn). Risk Engine взвешивает модель по её (пока низкой) уверенности.

**Фаза 3 — Анти-чит: локализация + GUI.**
- Персист языка per-UUID + починка переспроса (показывать селектор только если язык ещё не выбран).
- Вынести ВСЕ строки (GUI, ThreatState, freeze, alerts, причины детекта, plugin.yml) в `messages_en/ru`; убрать русские протечки из `messages_en.yml`.
- Редизайн GUI: чистый дашборд безопасности (иерархия, статусы, уверенность, навигация), полностью локализованный, без перегруза.

**Фаза 4 — Коллектор: автономный ИИ-модуль.**
- Пайплайн вне главного потока: lock-free очередь → worker → извлечение признаков → инференс → запись датасета; временной буфер последовательностей; confidence/UNKNOWN/human-review-очередь.
- Схема датасета со всеми требуемыми метаданными (label_source, model_version, collector_version, feature_schema_version, prediction, confidence, uncertainty).
- Починить O(n²) на главном потоке, `LinkedList.get(i)`, пересоздание `Random`, хардкод TPS/версии.

**Фаза 5 — Тесты, замеры, отчёт.**
- Набор сценариев (легит + подозрительные), метрики FP/FN, precision/recall/F1, калибровка.
- Замеры производительности (или чёткое описание, что измерять, если реальных замеров нет).
- Финальный отчёт: Коллектор / Анти-чит / Локализация / GUI / Производительность (Before→After).
